- kubectl get nodes -o wide(see how many nodes of a cluster has, -o wide is for more information like under which os the Kubernetes is running)

- kubectl version (see the version of the Kubernete)

- Kubernetes runs on the node. there are two main node, control-plane node and workder node. each node has kubelet installed which is basically the agent.

- kubectl get pods (see how many pods exists, under the ready column '1/2' indicates that inside this pod total 2 containers are there and 1 is ready)

- kubectl run nginx --image=nginx (create a pod inside the cluster, named nginx using the image of nginx. it basically create a container of web server and put it inside the pod)

- kubectl describe pod podname (shows all the information of that pod, example what images has been used to creating that pod, which node they belong, how many containers are there inside a pod, what images of each container, see the state of each container, under the event we can find out why that container failed)

- kubectl delete pod webapp (delete the webapp pod)

- kubectl run redis --image=redis123 --dry-run=client -o yaml > redis-definition.yaml (create the redis pod with the iamge, dry run: client means dont create the pod yet, instead create a .yaml file and store the following action in the yaml file)

- kubectl create -f redis-definition.yaml (create the pod using the manifest file or .yaml file)

- kubectl edit pod redis (edit the pod called redit to fix the image)

- kubectl apply -f redis-definition.yaml (after editing reapply the yaml file to update the pod)

- kubectl get replicaset (shows how many replica sets are there, suppose you want your database always up and running, so you make three identical conatainer, if one fails immediately jumps on 2nd replica)

- kubectl describe replicaset (shows the details as described earlier for replicaset)

- apiVersion = v1 is used for core resources like pods, services, configmap, and apps/v1 = for replicaset, deployment. 

- for a replicaset yaml file, the kind is the what type of service, like replicaset, under metadate then name : the name of the replicaset. and selector then lebel, then tier name. Kubernetes use the lebel name to group them. inside the template its for the pods. the lebel and template tier name has to be the same. spec got the container config.

- after editing the replicaset, delete the previous pods so that the new replica pods can start

- kubectl scale rs new-replica-set --replicas=5 (increase the replicas or number of pods)

- kubectl get deployment (see the number of deployment) + every other functionality are same as replicasets

- deployment is basically a manager of replicaset. here replicaset is making sure that desired pods always there if anything destorys. but the deployment happens based on replicaset. where it manage new version of pods. imagine v1 of 4 pods is running, a new version is appered v2. now the deployment influence the replicaset, by removing the v1 pod and creating a pod of v2. step by step one by one. reducing downtime.

- in deployment it got old replicaset and newreplicaset name. with pods container image and other information. it also has strategy. there are two type of strategy. one is rolling update, another is recreate. rolling update is 1 old replaced with 1 new, and so on. and the recreate is delete all the old pods and creates all the new.

- to test it in the deployment you change the pods containers image. now there is two version the old one and the image created with new one. when we run a test or request got hit in the service we can see all the version 2 pods. under the max unavailabe we can also see the max number of pod can be unavailable during the upgrating pods. we change the pods image in the deployment for a new update.

- kubectl get service.

- default kubernetes service type is clusterIp.

- pods have dynamic IPs, can die and restrart. so we cannot rely on pods. but service has a fixed dns name and a stable ip. forwards request to pods.

- you app is running on port 8080 inside the pods container. here target port is 8080. meaning sends traffic to port 8080 inside the pod.

- port is the Service port. port exposed by the service, typically any port.

- Client → Service:80 → Pod:8080

- here we hit in the browser : serverip:service_port. the service port take http, https request. the service port could be anything like 3000, 80, 443. then it forwards the request to the pods. the service port and target port can be same and commonly used.

- label is for identifying pod and selector is for choosing pod. (Service → selector → matches labels → sends traffic to Pods)

- Endpoint is the actual IP address of a Pod that a Service can send traffic to.

- service api version is v1, kind : Service. with all the information we can create a service with .yaml file and apply so that we can access the application.
